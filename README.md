## Контекст <a name="context"></a>

**ЕГИСЗ** — Единая государственная информационная система в сфере здравоохранения. Основное взаимодействие медицинской организации (МО) с ЕГИСЗ — передача структурированных электронных медицинских документов (**СЭМД**) в подсистему **РЭМД** (Реестр электронных медицинских документов). Каждый СЭМД (выписной эпикриз, протокол осмотра, направление, заключение и другие — десятки видов) подлежит регистрации в РЭМД.

Обмен с РЭМД двухфазный: синхронный технический ответ «принято к обработке» и асинхронный callback с результатом регистрации. Одной отправке СЭМД соответствуют минимум две строки в журнале обмена. Callback содержит либо `emdrId` зарегистрированного документа, либо список ошибок (валидация, подпись, справочники НСИ, бизнес-правила).

Наша компания — **интегратор**: между МИС клиник и инфраструктурой ЕГИСЗ работает проксирующий шлюз. Он принимает от МИС подписанный документ, маршрутизирует его в РЭМД, получает callback и возвращает результат клинике. Сообщения шлюз записывает в журнальную БД **`proxy_egisz`** (Firebird 5) — лог обмена для нужд шлюза, не предназначенный для аналитики.

Поверх этого лога работает наш сервис. Каждые 5 минут он инкрементально вычитывает новые строки журнала, парсит SOAP/XML, склеивает исходящее сообщение с callback, нормализует статусы и причины отказов и формирует витрину фактов для дашбордов Metabase.

## Описание прототипа сервиса <a name="service-overview"></a>

Сервис закрывает пять эксплуатационных задач.

**Контроль отправки.** Число сообщений в час и в день, разрезы по клинике и типу документа, провалы и всплески. Прекращение отправки клиникой фиксируется по графикам.

**Контроль обратной связи.** На каждое исходящее СЭМД должен приходить callback от РЭМД, корректно склеенный с оригиналом по идентификаторам (`messageId`, `relatesTo`, `localUid`, `emdrId`). Документ без callback за окно >24 ч — кандидат на эскалацию.

**Контроль ошибок.** РЭМД возвращает ошибки в виде XML-конвертов с десятками `<item>`, часть из которых содержит только машинный код. Сервис парсит этот XML и приводит каждую ошибку к одной из ~70 канонических категорий (СНИЛС пациента, специальность врача не в НСИ, истёкший сертификат, сетевой таймаут, дубликат и т. д.).

**Контроль полноты.** Документы без `emdrId`, со странным статусом, расхождения между журнальной таблицей и таблицей callback'ов, пустые обязательные поля.

**Контроль ETL-контура.** Курсор двигается, mat-view'ы свежие, lag DAG в норме, ошибок ETL нет. Под это выделен дашборд `02_service.json`.

## Архитектура и поток данных <a name="architecture"></a>

ELT-схема: Python в Airflow отвечает за извлечение и загрузку, трансформации выполняются в PL/pgSQL внутри DWH. Бизнес-логика парсинга XML, нормализации статусов, классификации ошибок и сборки фактовой таблицы сосредоточена в `db/parts/`.

| Компонент | База / технология | Что делает |
|---|---|---|
| Источник | Firebird 5, БД `proxy_egisz` | Журнал обмена шлюза. Только чтение. |
| Оркестратор | Apache Airflow 2.11.2, DAG `egisz_elt_dag` | Каждые 5 минут: дельта из источника, загрузка в DWH, SQL-трансформация, обновление mat-view'ов, продвижение курсора. |
| DWH | PostgreSQL, БД `dwh_egisz` | Raw-слой, справочники, фактовая таблица, ~17 PL/pgSQL-функций, 2 материализованных и 11 обычных view. |
| Визуализация | Metabase v0.60.2.5 | 6 дашбордов, ~75 native-карточек поверх mat-view и `v_rpt_*_ui`. |
| Деплой | Kubernetes (Docker Desktop) | Helm-чарт Airflow + манифест Metabase, bootstrap-скрипт `up.ps1`. |

Локальный dev-стенд: Airflow на `localhost:8080`, Metabase на `localhost:3000`. Служебные базы Airflow (`airflow_db`) и Metabase (`metabase_app`) изолированы от DWH.

Подключения хранятся в Airflow Connections с фиксированными именами: `proxy_egisz_fb` (Firebird) и `dwh_egisz_pg` (DWH). В DAG используется `BaseHook.get_connection` — переключение инстансов (например, на read-replica) выполняется без правок кода.

## Источник: прокси-БД интегратора (Firebird `proxy_egisz`) <a name="source"></a>

Из таблиц шлюза читаются четыре. Выборка инкрементальная по монотонному ключу через keyset-пагинацию (`WHERE col > :last_seen ORDER BY col ROWS :limit`).

**`EXCHANGELOG`** — основной журнал. Каждая строка — одно сообщение между шлюзом и РЭМД. Поле `MSGTEXT` хранит полный SOAP/XML payload и служит источником для парсинга идентификаторов документа, кода и названия СЭМД, статуса и ошибок. PK — `LOGID` (bigint, монотонный).

**`EGISZ_MESSAGES`** — таблица сообщений с короткими метаданными (`EGMID`, `MSGID`, `REPLY_TO`, `DOCUMENT_ID`, `CREATED_AT`). Используется для построения связи «исходящее ↔ callback», когда XML исходного и ответного сообщений лежат в разных строках `EXCHANGELOG`. PK — `EGMID`.

**`JPERSONS`** и **`EGISZ_LICENSES`** — справочные таблицы организаций и лицензий. Загружаются в `dim_organizations` и `dim_licenses` и позволяют по любому идентификатору из callback (`mo_uid` или GOST-хост) получить имя клиники.

Идентификаторы в обмене с РЭМД приходят в трёх формах: голый UUID, `urn:uuid:UUID`, `<urn:uuid:UUID>`. Функция `egisz_normalize_message_id()` приводит их к канонической форме; на нормализованное значение созданы функциональные индексы, обеспечивающие быстрые JOIN-ы независимо от формы хранения.

# Airflow

## ELT-конвейер Airflow <a name="elt-pipeline"></a>

DAG `egisz_elt_dag` собран на TaskFlow API, расписание `*/5 * * * *`, `max_active_runs=1`, размер батча `BATCH_SIZE = 5000`.

Последовательность задач:

```
sync_dimensions
  ▸ extract_from_proxy
    ▸ load_to_dwh
      ▸ analyze_raw_tables
        ▸ transform_data
          ▸ refresh_materialized_views
            ▸ update_watermark
```

| Задача | Действие |
|---|---|
| `sync_dimensions` | Полная перезагрузка `dim_organizations` и `dim_licenses` из Firebird через UPSERT по `ON CONFLICT`. |
| `extract_from_proxy` | Читает watermark из `elt_state`, забирает батч новых строк `EXCHANGELOG` и `EGISZ_MESSAGES`, дополнительно подтягивает старые сообщения по ссылкам из свежего XML — для сборки полной цепочки «исходящее + callback» в одной транзакции. |
| `load_to_dwh` | UPSERT в `exchangelog_raw` и `egisz_messages_raw` через `INSERT ... ON CONFLICT DO UPDATE`. Идемпотентна. |
| `analyze_raw_tables` | Запускает `ANALYZE` на загруженных в батче таблицах. Обновляет статистику планировщика после bulk-загрузки; без неё запросы к `exchangelog_raw` уходят в seq-scan мимо функциональных индексов. |
| `transform_data` | Вызывает `egisz_transform_raw_to_facts(min_log_id, max_log_id, min_egmid, max_egmid)`. Окно курсора в параметрах ограничивает функцию новыми строками. В обработку также включаются старые строки `exchangelog_raw`, к которым в текущем окне пришёл поздний callback. |
| `refresh_materialized_views` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` для `v_egisz_transactions_enriched_ui` и `v_stg_channel_errors_by_document`. CONCURRENTLY не блокирует параллельные SELECT от Metabase. |
| `update_watermark` | UPSERT в `elt_state` через `GREATEST(current, new)`. Выполняется последним: при сбое любого предыдущего шага watermark не двигается, и батч перечитывается на следующем прогоне. |

XCom-payload между тасками имеет фиксированную схему — `count`, `message_count`, `last_log_id`, `last_egmid`, `max_id`, `max_egmid`, `rows`, `message_rows`. Изменение схемы требует синхронной правки в `airflow/dags/egisz_elt_dag.py` и `AGENTS.md`.

# DWH

## DWH-модель <a name="dwh-model"></a>

Схема описана в `db/dwh_init.sql` (собиратель через `\i`) и 11 модулях в `db/parts/`. Миграционных файлов нет: DWH разворачивается одним прогоном `psql -f db/dwh_init.sql`, изменения схемы вносятся в нужный модуль через идемпотентные паттерны (`CREATE TABLE IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `ALTER TABLE ... IF EXISTS`, `INSERT ... ON CONFLICT`).

Слои:

| Слой | Состав |
|---|---|
| Raw | `exchangelog_raw`, `egisz_messages_raw` — строки журнала «как из Firebird». `elt_state` — watermark-курсоры. |
| Справочники | `dim_organizations`, `dim_licenses`, `dim_semd_types`. `dim_semd_types` заполняется seed-данными из `10_tables.sql`. |
| Факты | `fact_egisz_transactions` — одна строка = одна логическая транзакция «отправка СЭМД и её результат», независимо от числа физических сообщений в журнале. |
| Materialized views | `v_egisz_transactions_enriched_ui` — основная аналитическая витрина с русскоязычными алиасами для Metabase. `v_stg_channel_errors_by_document` — агрегат ошибок канала на уровне документа. |
| View отчётов | `v_rpt_*_ui` — `network_errors_detail`, `documents_no_response`, `semd_archive`, `clinic_connectivity_daily`, `connectivity_global_daily`, `error_interpretations`. |
| Health-view | `v_health_*_ui` — `by_clinic`, `proxy_db`, `signals`. Источники для дашборда `02_service.json`. |

Перечень колонок фактовой таблицы и индексов — в `db/parts/10_tables.sql`.

Порядок модулей обязателен и отражает порядок зависимостей:

| Модуль | Назначение |
|---|---|
| `00_bootstrap.sql` | Роль `egisz`, базовые GRANT'ы на схему `public`. |
| `10_tables.sql` | Таблицы, seed `dim_semd_types`, индексы. |
| `20_functions_parsing.sql` | Утилиты парсинга XML и нормализации идентификаторов. |
| `30_error_rules.sql` | Таблица `egisz_error_interpretation_rules` и seed правил. |
| `40_functions_errors.sql` | Функции классификации, сборки JSON ошибок, нормализации лейблов СЭМД. |
| `50_transform.sql` | Главная функция `egisz_transform_raw_to_facts`. |
| `60_drop_dependents.sql` | Дроп view'ов и legacy-колонок перед пересборкой. |
| `70_views_core.sql` | `v_egisz_transactions_enriched_ui` (MV) и `v_rpt_error_interpretations_ui`. |
| `75_views_stg.sql` | `v_stg_channel_errors_by_document` (MV) и `v_stg_channel_network_errors_by_document`. |
| `80_views_rpt.sql` | Все `v_rpt_*_ui`. |
| `90_views_health_and_finalize.sql` | `v_health_*_ui`, проверка GRANT'ов, `REFRESH MATERIALIZED VIEW`. |

Все объекты принадлежат роли `egisz`. Metabase подключается под read-only ролью `postgres`.

## Правила парсинга SOAP/XML <a name="parsing"></a>

Работа с XML выполняется на стороне PostgreSQL. Файл: `db/parts/20_functions_parsing.sql`.

### Архитектура парсинга

Главная функция `egisz_transform_raw_to_facts` выполняет парсинг в три прохода:

| Проход | Что извлекается | Откуда |
|---|---|---|
| 1 — идентификаторы и статус | `messageId`, `relatesTo`, `localUid`, `emdrId`, `semd_code`, `semd_name`, `status`, callback-URL, временны́е метки | `EXCHANGELOG.MSGTEXT` |
| 2 — ошибки | SOAP-faultcode, текст ошибки, список `<item>` | `EXCHANGELOG.MSGTEXT` (только для callback с ошибкой) |
| 3 — JSON ошибок | Нормализованный JSON `{code, message, type}` по каждому `<item>` | результат прохода 2 |

Правила парсинга проверяются прямыми SELECT'ами в БД без поднятия Airflow.

### Утилитные функции

| Функция | Назначение | Детали |
|---|---|---|
| `egisz_xml_text(payload, tag_name)` | Извлечение всех вхождений текста тега | Агностично к префиксу неймспейса; реализована через `regexp_matches`. Базовая функция для всех остальных. |
| `egisz_normalize_message_id(value)` | Нормализация UUID-идентификаторов | Приводит `<urn:uuid:...>`, `urn:uuid:...` и голый UUID к единой форме. На нормализованное значение — функциональные индексы `idx_egisz_messages_msgid_norm`, `idx_fact_egisz_message_id_norm`, `idx_fact_egisz_relates_to_norm`. |
| `safe_cast_timestamptz(p_text)` | Безопасный каст в `timestamptz` | Возвращает `NULL` вместо исключения. Используется потому что поля даты приходят в нескольких форматах (с/без таймзоны, ISO/локальный). |
| `egisz_clean_host(p_text)` | Нормализация хоста callback-URL | Подготавливает хост для JOIN со справочником `dim_licenses`. |
| `egisz_extract_jid_from_endpoint(p_text)` | Извлечение JID из URL | Из URL вида `gost-1234.infoclinica.lan` извлекает `1234` — внутренний ID организации. |
| `egisz_clean_text_value(p_text)` | Нормализация текстовых полей | Схлопывание пробелов, удаление BOM и неразрывных пробелов, обрезка. |
| `egisz_normalize_semd_code(p_text)` | Нормализация кода СЭМД | Разные версии шаблонов используют разные префиксы и суффиксы. |

Полные сигнатуры — в комментариях к `db/parts/20_functions_parsing.sql`.

### Нормализация идентификаторов

Один и тот же идентификатор сообщения встречается в трёх формах:

| Форма | Пример |
|---|---|
| Голый UUID | `dd73fc79-e2e6-479c-a285-2a470fc4f04e` |
| С префиксом | `urn:uuid:dd73fc79-e2e6-479c-a285-2a470fc4f04e` |
| В угловых скобках | `<urn:uuid:dd73fc79-e2e6-479c-a285-2a470fc4f04e>` |

Все три формы нормализуются к голому UUID. JOIN-ы между `exchangelog_raw`, `egisz_messages_raw` и `fact_egisz_transactions` работают по функциональным индексам на нормализованном значении.

## Классификация ошибок <a name="error-classification"></a>

РЭМД возвращает ошибки в нескольких формах: машиночитаемый код в SOAP-faultcode (`VALIDATION_ERROR`, `RUNTIME_ERROR`, `ASYNC_RESPONSE_TIMEOUT` и др.), текст, отдельные `<item>` внутри ответного XML (до десятка в одном callback), Schematron-фрагменты в человеческом тексте. Сырые `error_message` дают несколько тысяч уникальных формулировок — для агрегации в дашборде они приводятся к **69 каноническим категориям** (плюс `Неизвестная ошибка`).

Классификация декларативная: правила хранятся в таблице `egisz_error_interpretation_rules` (`db/parts/30_error_rules.sql`), применяет их функция `egisz_error_interpretation_type(error_code, error_message)` (`db/parts/40_functions_errors.sql`). Каждое правило — тройка `(match_code, match_pattern, interpretation)` с приоритетом.

Несколько `<item>` разных типов в одном callback дедуплицируются и склеиваются через ` · `. Если ни одно правило не сработало — `error_type = 'Неизвестная ошибка'`.

Результат классификации сохраняется в трёх полях фактовой таблицы:

- `error_type` — канонический тип для группировки в дашбордах.
- `error_summary` — краткая пользовательская интерпретация для карточек.
- `error_json_text` — полный JSON всех `<item>` в структуре `{code, message, type}` для drill-down.

View `v_rpt_error_interpretations_ui` раскрывает интерпретации построчно — для аудита правил.

### Группы ошибок

| Группа | Правила | Содержание |
|---|---|---|
| **Структурная валидация СЭМД** | 1, 4, 8, 11–15 | Schematron, XSD, парсинг XML, обязательные поля CDA-документа. |
| **Справочники НСИ** | 5, 13, 24–27 | Устаревшая версия справочника, отсутствующий код, неверное наименование. |
| **Регистры пациента и медработника** | 6–10, 17–23, 56, 57, 59, 60 | ФРМР, ФРМО, ГИП: несовпадение СНИЛС, должности, отчества, подразделения. |
| **Организация и лицензии** | 2, 3, 30, 37, 39, 65 | ОГРН в СЭМД не совпадает с ФРМО, лицензия не найдена, организация не привязана к РМИС. |
| **Регистрация ИС в РЭМД** | 31–33 | `ACCESS_DENIED`, `DISABLED_RMIS`, `NO_RMIS`. |
| **Электронная подпись и сертификаты** | 45–51 | Сертификат истёк, отозван, недействителен на дату документа, недоступен CRL/OCSP. |
| **Документооборот РЭМД** | 16, 28, 29, 34–36, 38, 40, 54, 58 | Документ уже зарегистрирован, не найден, запрос дублируется или аннулирован. |
| **Получение файла ЭМД из ИС** | 41–44 | `getDocumentFile` вернул ошибку, файл не передан, МИС недоступна. |
| **Технические ошибки РЭМД** | 52, 53, 62, 63, 66–68 | `INTERNAL_ERROR`, `RUNTIME_ERROR`, `ASYNC_RESPONSE_TIMEOUT`, недоступность УЦ. |
| **Сетевая ошибка** | 64 | Таймауты и обрывы между шлюзом и РЭМД. |
| **Неизвестная ошибка** | 69 | Финальный fallback. |

### Полный список правил классификации

Источник истины — `db/parts/30_error_rules.sql`. При добавлении нового правила seed расширяется через `INSERT ... ON CONFLICT (rule_code) DO UPDATE`.

| № | Группа | Тип ошибки | SOAP-код | Паттерн текста | Пример сообщения |
